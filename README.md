## Learning an Interpretable Traffic Signal Control Policy (Ault, Hanna & Sharon, AAMAS 2020)

- Paper: https://arxiv.org/abs/1912.11023
- Authors' code: https://github.com/jault/StateStreetSumo (single commit `af68c16`)
- Video: `<ADD GOOGLE DRIVE LINK>`

This repository is our **proof of work** for the assignment. It contains (1) code we wrote to check the paper's
definitions, (2) our runs of the authors' code in SUMO, and (3) independent checks of the numbers those runs produced.

**Scope.** We ran the authors' *actuated* baseline (one episode each for Low and Medium demand, two for High demand) and
**one exploratory DRHQ episode** on Low demand. We did **not** run the standalone DQN, DRQ or DRSQ agents in SUMO (the DRHQ agent trains a DQN internally as its teacher), we did **not** run the paper's
full protocol (40 episodes × 30 trials), and we do **not** claim to reproduce the paper's 19.4% / 30% delay reductions.

## 2. What we checked and what we found

### 2.1 Parameter count (Sec. 4)
`11 × (2·12 + 8) = 352` for the real intersection and `8 × (2·12 + 8) = 256` for the Fig. 1 layout. Both are asserted in
`checks/check_parameters_and_monotonicity.py`. The authors' `drxq.py` builds its polynomial as `DQNPolyMax((11, 16), ...)`:
11 actions × 16 inputs × (weight, exponent) = 352.

### 2.2 Monotonicity (Definition 1 / Lemma 1)
Eq. (1) is a product of the state-variable sum and the clearance-flag sum (confirmed against the typeset paper), and
`src/precedence.py` implements it that way.

2,400 random single-variable sweeps over random positive weights and random exponents: **0 sign changes**. A deliberately
non-monotone quadratic fails the same test (negative control), so the test can fail. Plot: `results/monotonicity.png`.

**Lemma 1 derivative.** The typeset proof gives ∂g/∂s[i] = w·p·s^(p−1)·Σ(…). The derivative of (w·s)^p is
p·w^p·s^(p−1), which differs by a factor w^(p−1). Our finite-difference check (w = 1.7, p = 1.6, s = 3.3) gives 7.655,
matching p·w^p·s^(p−1) = 7.655, not the printed form (5.568). The lemma's conclusion still holds for w > 0, because the
sign of the slope is the sign of p. We only tested positive weights; for w < 0 with fractional p the term is undefined, and
the paper does not state that weights must be positive.

### 2.3 Teacher–student comparison of DRQ / DRSQ / DRHQ (`src/teacher_student.py`)
A synthetic MLP "teacher" (16,203 parameters) stands in for the Q-network. A 352-parameter polynomial "student" is trained
to imitate it with three targets: squared error to Q (DRQ), cross-entropy to softmax(Q) (DRSQ), cross-entropy to one-hot
argmax Q (DRHQ). 10 seeds, held-out argmax agreement:

| Variant | Agreement with teacher | Q-value lost on disagreements |
|---|---|---|
| DRQ | 79.0% ± 1.4 | 0.044 |
| DRSQ | 82.5% ± 1.5 | 0.033 |
| DRHQ | 81.9% ± 1.2 | 0.039 |

Random action: 9.1%. "Most stopped vehicles" heuristic: 22.2%. Plot: `results/teacher_student_agreement.png`.
Re-run on our own laptop (Python 3.14) gave identical numbers in 314 s; see `evidence/`.

Reading: the two classification-style targets beat plain regression in 10 of 10 seeds. DRSQ and DRHQ are not distinguishable
(mean gap 0.6 points), so this experiment does **not** show DRHQ as the best variant. This agrees with Fig. 4, where the DRSQ
and DRHQ curves overlap. The teacher is synthetic, there is no RL and no SUMO, and we did not read `networks.py`, so this is a
sanity check of the target types only. Gradients were verified against finite differences.

### 2.4 The authors' actuated baseline, run in SUMO (`sumo_run/`)
Authors' actuated controller, headless, no code patches, one episode per run:

```
python -c "import main; main.run_trial('actu', <file>, 1, <trial>, render=False)"
```

| Demand (`--file`), trial | Trips | Missed | Mean time lost | Max delay | Rush-hour mean |
|---|---|---|---|---|---|
| Low (0), trial 0 | 47,088 | 0 | 42.14 s | 265.3 s | 64.31 s |
| Medium (1), trial 2 | 53,687 | 0 | 47.32 s | 331.2 s | 76.75 s |
| High (2), trial 3 | 64,395 | 0 | 54.71 s | 256.8 s | 75.85 s |
| High (2), trial 4 | 64,784 | 0 | 58.37 s | 377.5 s | 92.53 s |

Every number above was recomputed from each run's `tripinfo.xml` with `checks/recompute_delay_from_tripinfo.py`; the
compressed trip data are in `sumo_run/tripinfo/`. "Mean time lost" is the mean of SUMO's `timeLoss` per trip
(`traci_env.get_delay`).

**Run-to-run variation.** The two High runs use the same demand file and differ by 3.7 s (about 7%) in mean time lost,
16.7 s in rush-hour mean and 389 in trip count. The paper (§6.1) spawns vehicles randomly within each 5-minute interval, so
runs are not deterministic and a single run is only an indication. Fig. 4 averages 30 trials.

**Comparison with the paper's Fig. 4 (actuated controller; values read off the plot by eye, approximate).**

| Demand | Fig. 4 actuated (approx.) | Our runs |
|---|---|---|
| Low | about 42 s | 42.14 s |
| Medium | about 46 s | 47.32 s |
| High | about 67 s | 54.71 s and 58.37 s |

Low and Medium are single runs, so their agreement may partly be luck. Both High runs are below the paper's value, by about
13–18%. We could not explain this. SUMO 1.12.0 instead of the authors' 1.0.1 is an untested candidate.

**Where the paper's headline numbers come from (Fig. 4, read by eye).** Up to 19.4% matches DRHQ on low demand
(~34 s vs ~42 s, about 18.5%). Up to 30% matches the CMA-ES point on high demand (~47 s vs ~67 s, about 29%).
All readings are in `results/fig4_readings.md`.

### 2.5 One exploratory DRHQ episode (Low demand, trial 5)
The authors' DRHQ agent (`DRXQAgent`, `soft=False`), one fresh agent, one training episode, headless, no code patches:

```
python -c "import main; main.run_trial('drhq', 0, 1, 5, render=False)"
```

| Run | Trips | Missed | Mean time lost | Rush-hour mean (4,619 trips) | Max delay |
|---|---|---|---|---|---|
| DRHQ, 1 episode (trial 5) | 47,152 | 0 | **42.61 s** | **52.21 s** | 334.8 s |
| Actuated, Low (trial 0) | 47,088 | 0 | 42.14 s | 64.31 s | 265.3 s |

The episode took about 21 minutes (derived from file timestamps), about the same as an actuated episode. The run also wrote poly.fn (23,904 bytes, HDF5) and policy.net. poly.fn holds the polynomial's weights and exponents, each of shape (11, 16), which is 352 parameters. checks/print_poly_weights.py prints them (table: sumo_run/8_poly_weights.png, values: sumo_run/poly_drhq_low_trial5.csv). After one episode all 352 values differ from 1.0 by more than 0.001 (we did not check the starting values in networks.py), and there are no negative weights and no non-positive exponents.
Trip data recomputed with `checks/recompute_delay_from_tripinfo.py`; files in `sumo_run/` (`drhq_low_*`, `poly.fn`,
`tripinfo/drhq_low_trial5.xml.gz`, `7_drhq_low_result.png`).

Reading: this is **one run** with 5% random actions and an almost untrained policy. The overall mean is about 1% above the
actuated run, which is smaller than the 7% difference we saw between two identical High runs, so we draw **no conclusion**
about DRHQ versus actuated control. The rush-hour mean is about 12 s lower, but our two High runs differed by 16.7 s in
rush-hour mean, so we do not claim an improvement. The first-hour average (the authors' "dead hour") is much higher
(66.4 s vs 30.8 s, corrected); a plausible reason is an untrained policy early in the episode, which we did not test. The
paper states DRHQ is competitive with actuated control after one training episode; this run is consistent with that, but
does not confirm it. We do not compare the `steps` column (10,343 vs 55,001) because we did not check what each counts.

### 2.6 Observation: the printed "dead-hour" value appears to be divided by the wrong count
In `traci_env.get_delay()` (line 353) the function returns `dh_loss / rh_trips`, the dead-hour total divided by the
**rush-hour** trip count, although `dh_trips` is counted (line 349). Screenshot: `sumo_run/5_get_delay_source.png`.
The corrected value divides by the dead-hour trip count:

| Run | Printed by authors' code | Corrected | Dead-hour trips |
|---|---|---|---|
| Low (actuated) | 19.46 s | 30.85 s | 2,927 |
| Medium (actuated) | 27.56 s | 40.15 s | 3,476 |
| High, trial 3 (actuated) | 24.09 s | 37.40 s | 3,664 |
| High, trial 4 (actuated) | 26.25 s | 40.50 s | 3,723 |
| Low, DRHQ trial 5 | 41.92 s | 66.43 s | 2,915 |

It appears in all five runs. The paper reports average delay only, so we found no published number that uses this value.

### 2.7 Demand data vs the paper's Table 1
Each shipped demand file covers 14 hours (168 five-minute bins), matching the paper's 7 A.M.–9 P.M. window. Their sums
differ from Table 1 by 4–5%:

| Demand | Paper date | Shipped file | Paper Table 1 | Simulated trips |
|---|---|---|---|---|
| Low | May 6, 2019 | 47,058 | 45,112 | 47,088 (actuated), 47,152 (DRHQ) |
| Medium | May 1, 2019 | 53,848 | 51,298 | 53,687 |
| High | June 21, 2019 | 64,489 | 61,261 | 64,395 and 64,784 |

We could not reconcile these. Dividing Table 1's totals by its stated average rates gives about 12 h, not 14 h; we report this
as an unexplained inconsistency, not as an error in the paper.

## 4. How to reproduce

Our scripts (Python 3, `numpy`, `matplotlib`, `scikit-learn`):

```
pip install -r requirements.txt
python checks/check_parameters_and_monotonicity.py
python checks/table1_and_arithmetic_checks.py <path-to>/StateStreetSumo/utils
python src/teacher_student.py 10
python checks/print_poly_weights.py sumo_run/poly.fn
```

Recompute the delay metrics from the stored trip data, without SUMO (Low: `--rush 33900`; Medium and High: `--rush 34200`):

```
python checks/recompute_delay_from_tripinfo.py sumo_run/tripinfo/low_trial0.xml.gz --rush 33900 --dead 0
python checks/recompute_delay_from_tripinfo.py sumo_run/tripinfo/drhq_low_trial5.xml.gz --rush 33900 --dead 0
```

The authors' code (inside their cloned repo, with `SUMO_HOME=/usr/share/sumo`):

```
python -c "import main; main.run_trial('actu', 0, 1, 0, render=False)"
python -c "import main; main.run_trial('drhq', 0, 1, 5, render=False)"
python <this-repo>/checks/recompute_delay_from_tripinfo.py Data0-0/tripinfo.xml --file 0
```

**Why we did not run the full protocol.** One actuated episode took about 20 minutes and one DRHQ episode about 21 minutes.
The paper's curves use 40 episodes × 30 trials, so extrapolating from our single measurements gives roughly 14 h per trial
and about 420 h per method per demand level. This is an extrapolation from one DRHQ episode on Low demand; later episodes
and other demand levels may take longer.

## 5. Limitations
- One actuated episode for Low and Medium and two for High. The two High runs differ by about 7% in mean delay, so there are
  no confidence intervals and single-run comparisons with the paper are only indicative.
- DRHQ: one exploratory episode on Low demand only. No standalone DQN, DRQ or DRSQ runs in SUMO, so no comparison against the paper's
  learning curves.
- The teacher–student experiment uses a synthetic teacher and is not RL.
- SUMO 1.12.0 instead of 1.0.1.
- Fig. 4 values are read by eye (about ±1 s).
